## 二、核心模块拆解
### 2.1 业务配置中心（ServiceConfiguration）
**业务价值**：这是整个系统最核心的模块。每家门店要对接哪些互联网医院、走什么渠道（POS/百姓通/小程序）、开什么类型的处方（西药/中药、医保/非医保）、需要什么合规校验（网院审方/合理用药/医保合规），全在这里配置。可以理解为处方流转的"开关矩阵"。

**核心字段**：

| 配置维度 | 字段 | 说明 |
| --- | --- | --- |
| 门店 | storeCode | 关联门店主数据 |
| 互联网医院 | netHospitalCode | 对接哪家网院 |
| 业务类型 | medInsureType | 非医保 / 统筹医保 / 非统筹医保 |
| 处方类型 | drugType | 西药 / 中药 |
| 问诊类型 | applyType | 图文 / 视频 |
| 渠道 | channel | POS / 百姓通 / 小程序 |
| 合规开关 | needNetHospitalCheck, needDrug, needRationalCheck, needYbCheck | 各项校验的开关 |
| 小程序专属 | isIdCardRequired, isFirstVisitRequired | 仅小程序渠道显示且必填 |


**技术含量**：

1. **动态表单校验**：当渠道选择 `MINI_MEMBER`（小程序）时，身份证和初诊信息字段才变为必填。使用 `computed` 动态计算校验规则，而非静态rules对象。这是因为Element Plus的校验器在初始化时绑定，静态rules修改后不会生效。
2. **互联网医院联动配置**：选择互联网医院后，调用 `getNetHospitalRequiredConfig` 接口获取该医院的必填字段配置。如果返回包含 `isIdCardRequired`，则强制将身份证设为必填且禁用修改（医院要求的合规底线，运营不能关闭）。
3. **非小程序渠道的字段清洗**：提交时，如果渠道不是小程序，将 `isIdCardRequired` 和 `isFirstVisitRequired` 设为 `null`，避免脏数据写入后端。

**操作链路**：

```plain
列表查询 → 搜索/筛选 → 修改 → 动态表单校验 → 提交 → 刷新列表
                      → 日志 → 侧边栏抽屉 → 无限滚动加载
                      → 导入 → 下载模板 → 上传文件 → 服务端校验 → 提交
                      → 导出 → Blob下载 → 错误检测 → 保存文件
                      → 开启/关闭 → 二次确认 → 调用接口 → 刷新列表
```

### 2.3 处方数据查询（Prescriptiondata）
**业务价值**：查询全量处方流转记录，是运营排查问题的核心入口。

**列表页**支持多维度筛选：处方ID、战区、经营归属、门店（远程搜索+无限滚动）、互联网医院、业务类型、处方类型、问诊类型、端口、时间范围（默认最近3天）。

**详情页**展示处方全貌：

+ **业务数据**：处方ID、门店、战区、网院、问诊类型、业务类型、状态、失败原因
+ **处方图片**：支持大图预览
+ **用户数据**：姓名、年龄、性别、孕期状态、诊断
+ **订单数据**：总金额、医保金额、现金金额
+ **药品数据**：药品名称、编码、数量（中西药差异化展示）、批号
+ **违规数据**：违规原因、流程影响

**技术含量**：

1. **医保费用的整数缩放计算**：

```javascript
const dealMedicareFee = computed(() => {
    const factor = Math.pow(10, 4) // 放大10000倍
    const { medicareFee, medSelfFee } = gotoutData || {}
    if (typeof medicareFee !== 'number' && typeof medSelfFee !== 'number') {
      return ''
    }
    const fee = (Math.round(factor * Number(medicareFee || 0)))
              + (Math.round(factor * Number(medSelfFee || 0)))
    return fee / factor
})
```

JavaScript浮点运算有精度问题（`0.1 + 0.2 = 0.30000000000000004`）。在医保金额计算中，这种误差会累积。用 `*10000 → 取整 → 加法 → /10000` 的方式，把浮点运算转化为整数运算。保留4位小数是因为医保金额精确到分（2位），多保留2位是为了中间计算不丢精度。

2. **中西药数量差异化展示**：

```javascript
newval.drugList.forEach((item) => {
    if (Number(newval.drugType)) {
        // 中药固定展示剂数
        item.value = `${item.applyQuantity}`
    } else {
        // 西药展示数量+单位
        item.value = `${item.applyQuantity}${item.drugUnit}`
    }
})
```

中药的 `applyQuantity` 代表剂数（如"3剂"），西药的代表剂量（如"10mg"）。同一个字段，不同业务含义，前端做差异化渲染。

3. **列表与详情的同页切换**：不用路由跳转，用 `v-if` 切换 `showTable` 状态。好处是列表的搜索条件和分页状态保存在组件内存中，返回时不需要重新请求。

```javascript
const checkBtnShow = (type) => {
```

#### aedFrom — 动态表单容器
通过 `types` prop切换不同的表单组件，用 `shallowRef` 持有组件引用。父组件通过 `RefChild.value.submit()` 命令式调用子组件的提交方法。

```javascript
const components = shallowRef();

  switch (value) {
    case "StoreManagement": components.value = StoreManagement; break;
    case "ServiceConfiguration": components.value = ServiceConfiguration; break;
```

```javascript
const escapeHtml = (str) => {
```

## 三、技术架构亮点
### 3.1 CAS SSO + 组织权限平台的双通道认证
**问题**：系统需要对接两套独立的认证体系——CAS（中央认证服务）负责"你是谁"，组织权限平台负责"你能看什么"。且权限平台不缓存登录态，每次都需要重新验证。

**方案**：

```plain
用户访问URL
  │
  ├─ 无ticket/token ──→ CAS重定向(cas.lbxdrugs.com) ──→ 带ticket回调
  │
  ├─ 有ticket ──→ createTokenByTicket()换token ──→ 存Cookie
  │
  └─ 有authorInfo(CSS平台嵌入) ──→ base64解码取token ──→ 存Cookie
  │
  ▼
router.beforeEach (permission.js)
  │
  ├─ findUserInfo() ──→ 获取用户名
  │
  └─ findMenuByUserId({appId}) ──→ 获取菜单权限树
       │
       └─ parserPermission(asyncRoutes, menu_list)
            │  递归匹配 route.relativeURL === menu.url
            │  深拷贝匹配到的路由，递归处理children
            │
            └─ router.addRoute() 逐条注入 ──→ 路由表构建完成
```

支持两条认证路径：

1. **CAS票据模式**：标准CAS SSO流程，URL带ticket时调 `createTokenByTicket` 换token
2. **CSS平台透传模式**：从 `authorInfo` query参数解码base64获取token（用于嵌入运营平台场景）

权限过滤的核心函数 `parserPermission`：

```javascript
export function parserPermission(routes, menus) {
  const tmp_arr = []
  _.forEach(routes, function(v, i) {
    _.forEach(menus, function(w, j) {
      if (v.relativeURL === w.url) {
        const c_v = deepClone(v)
        if (c_v.children && c_v.children.length > 0) {
          c_v.children = parserPermission(c_v.children, menus)
        }
        tmp_arr.push(c_v)
      }
    })
  })
  return tmp_arr
}
```

**效果**：权限完全由后端平台管控，前端零硬编码。新增菜单只需在权限平台配置，前端无需发版。

### 3.2 双Axios实例的微服务网关适配
**问题**：后端有两套独立的网关——业务微服务（`/lbx-ms-biz-rp-manage`）和框架级服务（Zuul网关 `msapi.lbxcn.com:31443`），响应格式和鉴权方式不完全一致。

**方案**：维护两个Axios实例，差异化处理：

| 差异点 | request.js（业务） | request_fwk.js（框架） |
| --- | --- | --- |
| baseURL | 业务微服务路径 | Zuul网关地址 |
| appCode header | 有 | 有 |
| 响应成功判断 | `code !== 0 && code !== 200` | `code !== 0` |
| "已存在"特殊处理 | 无 | `msg.includes('已存在')` 返回res而非reject |
| 返回值 | `res.data || res` | `res`（完整响应） |


两个实例共享统一的错误码拦截——`1001502` 触发自动登出+CAS重定向：

```javascript
if (res.code === 1001502) {
  setTimeout(() => {
    sessionStorage.clear()
    window.location.href = process.env.VUE_APP_SYSTEM_CASURL
      + '/cas/logout?service=' + window.location.href
  }, 2500) // 延迟2.5秒，让用户先看到错误提示
}
```

**效果**：两套后网关的差异被封装在请求层，业务组件无感知。新增接口只需选择对应的实例即可。

### 3.4 门店远程搜索的三级差异化节流
**问题**：el-select的 `remote-method` 和 `v-infinite-scroll` 共用同一个数据源，但"搜索"和"翻页"两种行为对响应速度的要求不同。搜索需要快响应，翻页可以慢一些，正在加载时要更慢防抖。

**方案**：

```javascript
setTimeout(() => { ... }, scrollDisabled.value ? 100 : storeLoading.value ? 1200 : 800)
```

| 状态 | 延迟 | 原因 |
| --- | --- | --- |
| `scrollDisabled=true`（首次搜索或最后一页） | 100ms | 用户刚输入，需要快速响应 |
| `storeLoading=true`（正在搜索中） | 1200ms | 避免频繁请求打爆后端 |
| 其他（翻页加载） | 800ms | 平衡体验和请求频率 |


同时，`v-infinite-scroll` 的disabled条件做了三重保护：

```html
:infinite-scroll-disabled="storeLoading || scrollDisabled ||
  (!storeVisible && !storeLoading && !scrollDisabled)"
```

**效果**：搜索体验流畅（100ms响应），翻页不卡顿（800ms），正在加载时不重复请求（1200ms防抖），下拉框关闭后滚动页面不会触发加载。

### 3.5 Excel导出的Blob错误检测
**问题**：当Axios的 `responseType: 'blob'` 时，所有响应都会被当作Blob处理。如果服务端返回的是JSON错误信息而不是Excel文件，它也会是Blob。不处理的话，用户会下载一个包含JSON错误信息的 `.xlsx` 文件，打开后是乱码。

**方案**：

```javascript
await exportApiFunc({ ...formInline }).then(async (res) => {
  // 检测Blob是否实际是JSON错误
  if (res instanceof Blob && res.type === 'application/json') {
    try {
      const text = await readFileAsText(res);
      const data = JSON.parse(text);
      if (data.code !== 0) {
        ElMessage({ message: data.message || data.msg || 'Error', type: 'error' });
        return;
      }
    } catch (error) {
      console.error('Error reading the blob as text:', error);
      return;
    }
  }
  // 正常文件流处理
  downloadBlob(res, downFileName);
})
```

**效果**：错误场景下不会下载损坏文件，而是正确显示错误提示。这个逻辑后来被提取为通用函数 `exportXlsx`，所有导出功能复用。

### 3.7 组件通信架构
**问题**：6人团队并行开发多个模块，需要统一的组件通信模式，避免混乱。

**方案**：建立三层通信规范：

| 层级 | 方式 | 适用场景 |
| --- | --- | --- |
| 父子组件 | Props + Emits + Expose | 表单弹窗、表格组件 |
| 跨页面 | URL Query + 条件渲染 | 列表→详情切换 |
| 全局状态 | Vuex（6个模块） | 用户信息、权限、标签页 |


**aedFrom的"壳组件+动态子组件+命令式调用"模式**：

```plain
ServiceConfiguration.vue（业务页面）
  │
  ├─ Props: openadd, lodatitle, types, formId, formData
  │
  └─ aedFrom/index.vue（壳组件）
       │  shallowRef动态切换子组件
       │
       └─ ServiceAed/index.vue（表单组件）
            Expose: submit(), romve()
            ← 父组件通过 RefChild.value.submit() 调用
```

**效果**：表单弹窗的逻辑被封装在壳组件中，业务页面只需控制 `openadd` 和 `types` 即可。

### Q2：技术栈为什么选Vue 3而不是React？
**回答**：这个项目是后台管理系统，Element Plus生态成熟、开箱即用，Vue 3的Composition API足够应对业务复杂度。团队成员的Vue经验更丰富，上手成本低。对于这种CRUD密集型的管理系统，Vue + Element Plus的开发效率是最高的。

### Q3：权限系统是怎么设计的？
**回答**：采用CAS SSO + 组织权限平台的双通道认证。CAS负责身份认证（你是谁），权限平台负责授权（你能看什么）。前端通过 `findMenuByUserId` 接口获取用户的菜单树，再用 `parserPermission` 函数递归匹配路由的 `relativeURL` 字段，最后通过 `router.addRoute()` 动态注入。

**追问**：为什么不用vuex存权限，而是动态注入路由？

→ 动态注入路由的好处是：没有权限的路由根本不会注册，用户即使手动输入URL也无法访问。如果只在vuex里存权限标志，路由本身是存在的，需要在每个页面的 `onMounted` 里检查权限，容易遗漏。

**追问**：parserPermission的性能怎么样？路由多了会不会卡？

→ 目前路由数量在20个以内，两层forEach的O(n*m)复杂度完全可以接受。如果未来路由数量增长到100+，可以改为Map索引，将复杂度降到O(n)。

### Q4：门店搜索下拉框是怎么实现无限滚动的？
**回答**：使用 `useStoreSelect` Composable，结合el-select的 `remote-method` 和Element Plus的 `v-infinite-scroll` 指令。搜索时调用 `storeQuest` 清空列表并请求第一页，滚动到底部时调用 `scrollLoad` 加载下一页并concat到列表中。

**追问**：节流是怎么做的？

→ 采用了三级差异化延迟：首次搜索100ms（快速响应），正在加载中1200ms（防抖），翻页加载800ms（平衡体验）。这是因为搜索和翻页共用同一个数据源，但对响应速度的要求不同。

**追问**：下拉框关闭后滚动页面会触发加载吗？

→ 不会。`v-infinite-scroll` 的disabled条件有三重保护，其中 `!storeVisible` 确保下拉框关闭后不触发加载。

### Q5：导出功能的Blob错误检测是怎么做的？
**回答**：当Axios的 `responseType: 'blob'` 时，所有响应都是Blob。如果服务端返回JSON错误信息，它的 `type` 是 `application/json` 而不是Excel的MIME类型。通过检测 `res.type === 'application/json'`，读取Blob内容并JSON解析，如果是错误则显示提示，否则正常下载文件。

**追问**：为什么要用readFileAsText而不是直接toString？

→ Blob的 `toString()` 返回的是 `[object Blob]`，不是内容。必须用 `FileReader.readAsText()` 读取Blob的内容。

### Q6：医保金额计算为什么要用整数缩放？
**回答**：JavaScript的IEEE 754浮点运算有精度问题，`0.1 + 0.2 !== 0.3`。在医保金额计算中，这种误差会累积导致金额对不上。用 `*10000 → 取整 → 加法 → /10000` 的方式，把浮点运算转化为整数运算，避免精度丢失。

**追问**：为什么是10000而不是100？

→ 医保金额精确到分（2位小数），但中间计算可能涉及更精确的比例。保留4位小数给中间计算留了余量，最终展示时再四舍五入到2位。

### Q7：XSS防护是怎么做的？

**追问**：为什么不直接用textContent？
