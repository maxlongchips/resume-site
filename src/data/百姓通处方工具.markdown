## 项目全局概览
**项目名称**：百姓通H5处方开方审方系统（`bxt-h5-prescription`）

**业务定位**：为连锁药店店员提供移动端处方流转工作台——涵盖开具处方、AI拍照识别处方、药师审方、人工调配、复核发药、凭证管理、视频问诊等全流程功能，内嵌于百姓通原生App中运行。

**技术栈**：Vue 3 + TypeScript + Vite + Vant 4 UI + Tailwind CSS + Vuex + vue-router，配套 Aegis 监控、GIO 埋点、腾讯云 COS、TRTC 音视频、WebSocket 实时通信。

**个人角色**：李强（你）提交 **142 个 commit**，占总量 1,044 的 **13.6%**，为项目第 3 高贡献者（前两位为 229、151）。代码规模：102 个 Vue 文件 + 56 个 TS 文件，**3.3MB / 32,593 行**。

## 二、技术架构亮点
### 架构模式
+ **单例平台适配层** (src/utils/platformTool.ts)：通过抽象基类 + iOS/Android/PC 多态实现，封装原生能力（扫码、获取用户信息、视频通话、导航栏控制），H5与Native桥接解耦
+ **Composition API 驱动**：全项目采用 Vue 3 `<script setup>` + Composition API，配合自定义 hooks（useSignature）实现逻辑复用
+ **分层状态管理**：Vuex 按业务模块拆分为 `user`、`aiPrescription` 两个 namespace，AI处方模块的状态（多步骤表单、AI回填映射）独立管理
+ **动态路由API包装器**：Axios 拦截器统一注入 token/app_id、统一错误码白名单处理（0/200），通过 `RequestConfig` 支持请求级 toast 控制

### 性能优化
+ **COS并发上传** (src/views/voucherDetails/index.vue:528-611)：多文件上传从串行改为 `Promise.all` 并发，显著缩短凭证影像上传时间
+ **签章墨迹智能裁剪** (src/components/SignatureBoard/index.vue:97-185)：像素级扫描识别墨迹边界，等比例缩放居中至标准尺寸(378×157)，保证签章图像一致性同时减小体积
+ **请求防串扰机制** (src/views/prescriptionList/index.vue:27)：通过递增 `requestId` 序列号，避免分页列表快速切换时数据错乱
+ **操作防重复点击锁** (src/views/reviewDispenseDetail/index.vue:48)：`isActionLoading` 标记 + 关键操作按钮禁用，防止重复提交
+ **轮询优化**：处方审核、签章合成等异步流程从固定30s轮询优化为5s/10s，并增加组件卸载标记防止内存泄漏

### 工程化建设
+ **Vite 构建**：postcss-px-to-viewport 自动适配移动端（375px基准），@vitejs/plugin-legacy 兼容旧浏览器
+ **代码规范**：ESLint + Prettier + Husky pre-commit + lint-staged 自动化检查
+ **监控体系**：Aegis SDK 全量错误监控 + 接口异常上报 + SPA路由PV追踪；GIO SDK 用户行为埋点（处方详情、调配复核、远程审方等关键事件）
+ **灰度发布**：基于字典接口的动态配置，实现签章功能、记录按钮、互联网医院接入的灰度开关控制
+ **Docker + Nginx** 容器化部署，支持 test/test2/uat/production 多环境

### 1. AI处方的策略模式表单引擎

+ 每个步骤（患者信息 → 药品选择 → 诊断录入 → 配药）实现 `StepStrategy` 接口（types.ts:187），包含 `layout`、`getConfig()`、`validate()`

**简历表述**：设计并实现了一套声明式表单策略引擎，将多步骤AI处方录入流程抽象为可配置的策略模式，支持中西药方差异化表单校验与动态字段渲染，新增业务步骤无需修改UI层代码。

### 4. 多级Token认证链与门店匹配
用户认证不是简单的"登录拿Token"，而是一条4步链式调用（tribunal/tools.ts:148-201）：

```plain
百姓通票据(ticket, 几分钟有效) 
  → 置换token(24h有效) + 人资编码(rzCode) 
  → 查询门店列表 
  → deptId匹配默认门店(过滤已闭店)
```

任何一步失败都有明确的错误提示，且 `userAuthInit` 支持业务回调注入，授权流程与业务逻辑解耦。

---

### 5. 人脸识别的递归重试闭环
tribunal/tools.ts:211-296 中的 `checkFaceVerification` 实现了一个完整的**人脸认证状态机**：

+ 先查接口判断是否需要人脸认证（支持灰度名单）
+ 需要认证 → 弹窗提示 → 调起 Native 人脸比对
+ 成功 → 记录结果到后端 → 更新本地缓存
+ 失败 → 弹窗"再次比对" → 递归调用自身，形成重试闭环
+ 服务异常时默认放行（不阻塞业务流程，降级策略）

**简历表述**：设计人脸识别认证的递归重试机制，包含灰度名单校验、Native人脸比对、成功/失败双回调分支、服务异常降级放行等完整兜底策略，确保合规要求下的用户体验不中断。

### 7. 处方药品对品匹配系统
prescriptionCompare 模块实现了一套院外处方药品与门店库存的**逐项比对工作流**：

+ 三态模型：`pending`（待对品）→ `completed`（已完成）→ `unmatchable`（暂无配对）
+ 进度条实时反馈（已完成数/总数）
+ 批号级别精细匹配：每个药品可展开多个批号，各自记录数量
+ 从比对结果直接跳转"单品比对"详情页（productCompare）

## 一、架构设计类
### Q1: 为什么在 Vue 3 项目中选择了 Vuex 而不是 Pinia？遇到了什么问题？
**回答要点：**

+ 项目启动时（2023年初）Pinia 生态尚不成熟，团队对 Vuex 更有经验，选择了 Vuex 4
+ **遇到的坑**：Vuex strict mode 下，通过 `<font style="background-color:rgba(0, 0, 0, 0.05);">mutateState</font>` 通用 mutation 直接修改 state 上的 ref 对象时，会触发深度监听的告警。README 中有明确记录
+ **解决方案**：使用了通用的 `<font style="background-color:rgba(0, 0, 0, 0.05);">mutateState(state, payload)</font>` mutation，通过 `<font style="background-color:rgba(0, 0, 0, 0.05);">Object.assign</font>` 方式合并属性，避免逐个字段写 mutation
+ **反思**：如果重新选型，会选 Pinia——更简洁的 API、更好的 TS 支持、不需要命名空间

### Q2: 项目中有两套 API 层（`<font style="background-color:rgba(0, 0, 0, 0.05);">xxx.ts</font>` 和 `<font style="background-color:rgba(0, 0, 0, 0.05);">xxx-duplicate.ts</font>`），为什么要这样设计？如何保证平滑迁移？
**回答要点：**

+ **背景**：后端在做 API 网关迁移，老网关 `<font style="background-color:rgba(0, 0, 0, 0.05);">/lbx-ms-biz-rp-store</font>` → 新网关 `<font style="background-color:rgba(0, 0, 0, 0.05);">/lbx-ms-prescription-open</font>`，新网关要求请求参数携带 `<font style="background-color:rgba(0, 0, 0, 0.05);">app_id</font>`
+ **策略**：采用**双跑并行**策略而非大爆炸式切换
    - 旧文件（`<font style="background-color:rgba(0, 0, 0, 0.05);">podium.ts</font>`、`<font style="background-color:rgba(0, 0, 0, 0.05);">user.ts</font>`）保持对老网关的调用
    - 新文件（`<font style="background-color:rgba(0, 0, 0, 0.05);">podium-duplicate.ts</font>`、`<font style="background-color:rgba(0, 0, 0, 0.05);">user-duplicate.ts</font>`）指向新网关，通过 `<font style="background-color:rgba(0, 0, 0, 0.05);">withAppId</font>` 辅助函数自动注入 `<font style="background-color:rgba(0, 0, 0, 0.05);">app_id</font>`
+ **降级方案**：老接口始终保留，如果新网关出问题，组件层面只需改 import 路径即可回退
+ **迁移进度**：已迁移的端点在新文件中，未迁移的仍在旧文件中，逐步推进

### Q3: 你如何设计原生能力（扫码、人脸识别、视频通话）的桥接层？
**回答要点：**

+ **三层抽象**：
    1. `<font style="background-color:rgba(0, 0, 0, 0.05);">BasePlatform</font>` 抽象类定义统一接口（`<font style="background-color:rgba(0, 0, 0, 0.05);">scanCode</font>`、`<font style="background-color:rgba(0, 0, 0, 0.05);">getUserInfo</font>`、`<font style="background-color:rgba(0, 0, 0, 0.05);">getToken</font>` 等）
    2. `<font style="background-color:rgba(0, 0, 0, 0.05);">AndroidP</font>` / `<font style="background-color:rgba(0, 0, 0, 0.05);">IosP</font>` / `<font style="background-color:rgba(0, 0, 0, 0.05);">PCP</font>` 三个平台实现，封装 `<font style="background-color:rgba(0, 0, 0, 0.05);">window.android.xxx()</font>` 和 `<font style="background-color:rgba(0, 0, 0, 0.05);">window.webkit.messageHandlers.xxx.postMessage()</font>` 的差异
    3. `<font style="background-color:rgba(0, 0, 0, 0.05);">PlatformTool</font>` 单例 + 工厂模式，根据 `<font style="background-color:rgba(0, 0, 0, 0.05);">navigator.userAgent</font>` 自动检测平台并实例化
+ **额外兜底**：`<font style="background-color:rgba(0, 0, 0, 0.05);">native.js</font>`（500+ 行）作为第二套老桥接层，直接挂在 `<font style="background-color:rgba(0, 0, 0, 0.05);">window</font>` 上供原生调用
+ **iOS vs Android 差异处理**：
    - iOS 通过 `<font style="background-color:rgba(0, 0, 0, 0.05);">messageHandlers</font>` 异步通信，Android 通过同步方法调用
    - 返回值字段名不同（如 `<font style="background-color:rgba(0, 0, 0, 0.05);">deptname</font>` vs `<font style="background-color:rgba(0, 0, 0, 0.05);">deptName</font>`），在 `<font style="background-color:rgba(0, 0, 0, 0.05);">getUserInfo</font>` 中做了字段映射归一化
+ **调试支持**：PC 端用 `<font style="background-color:rgba(0, 0, 0, 0.05);">PCP</font>` mock 类，可以在浏览器中模拟所有原生能力

## 二、复杂业务实现类
### Q4: 处方详情页是整个业务的核心页面，1737 行代码。你是如何管理这种复杂的状态机的？
**回答要点：**

+ **多角色多状态状态机**：页面涉及 3 个角色（医生、药师、店员）× 多种状态（待确认、待问诊、开方成功/失败、审方通过/驳回、远程审方中、已过期），组合出约 15+ 种 UI 状态
+ **设计思路**：
    - **状态驱动 UI**：所有状态判断收敛到 computed 属性（`<font style="background-color:rgba(0, 0, 0, 0.05);">showSuccess</font>`、`<font style="background-color:rgba(0, 0, 0, 0.05);">showError</font>`、`<font style="background-color:rgba(0, 0, 0, 0.05);">bottomOptBtnGroup</font>` 等），模板中只做 `<font style="background-color:rgba(0, 0, 0, 0.05);">v-if</font>` 判断，不写逻辑
    - **按钮组动态生成**：`<font style="background-color:rgba(0, 0, 0, 0.05);">bottomOptBtnGroup</font>` computed 根据角色 + 状态 + 渠道类型，动态返回应显示的按钮数组（含文字、事件、样式），模板用 `<font style="background-color:rgba(0, 0, 0, 0.05);">v-for</font>` 渲染
    - **操作锁**：`<font style="background-color:rgba(0, 0, 0, 0.05);">isActionLoading</font>` 作为互斥锁，防止审核通过/驳回重复提交
+ **渠道差异化**：O2O/B2C/粤医保/三品堂/国家处方流转平台 各有不同的按钮显示和文案规则，通过 `<font style="background-color:rgba(0, 0, 0, 0.05);">channelType</font>`、`<font style="background-color:rgba(0, 0, 0, 0.05);">medInsureType</font>`、`<font style="background-color:rgba(0, 0, 0, 0.05);">billManagement</font>` 等字段组合判断
+ **处方图片优先级链**：`<font style="background-color:rgba(0, 0, 0, 0.05);">dispenseStatus === 20</font>`（调配完成）→ `<font style="background-color:rgba(0, 0, 0, 0.05);">pharmacistCheckStatus === 20</font>`（药师已审核）→ 原始处方图片，确保展示最新、最权威的签章版本

### Q5: 为什么同时用了 WebSocket 和 HTTP 轮询？它们之间如何协同？
**回答要点：**

+ **双重保障机制**：WebSocket 是主通道，HTTP 轮询（5 秒间隔）是 fallback
    - WebSocket 负责接收医生开方结果（`<font style="background-color:rgba(0, 0, 0, 0.05);">doctorCheckStatus</font>` 变更）
    - 轮询调用 `<font style="background-color:rgba(0, 0, 0, 0.05);">getInfoProcess</font>` 接口作为兜底，防止 WebSocket 断开或消息丢失
+ **协同方式**：两者并行运行，谁先拿到结果谁触发状态更新，通过 Vuex `<font style="background-color:rgba(0, 0, 0, 0.05);">consultWSResult</font>` 统一存储结果，watcher 监听变化触发 UI 更新
+ **WebSocket 实现细节**：
    - 使用 `<font style="background-color:rgba(0, 0, 0, 0.05);">tools-vue3</font>` 的 `<font style="background-color:rgba(0, 0, 0, 0.05);">WebSocketBean</font>` 封装，自带重连机制（3 秒间隔）
    - 心跳 3 秒一次
    - WS URL 前缀通过字典接口动态获取（支持灰度），失败时降级到环境变量
+ **远程审方的独立轮询**：EPS 远程审方有另一套独立的 5 秒轮询（`<font style="background-color:rgba(0, 0, 0, 0.05);">getInfoForBxt</font>`），通过 `<font style="background-color:rgba(0, 0, 0, 0.05);">localStorage</font>` 持久化轮询状态（key: `<font style="background-color:rgba(0, 0, 0, 0.05);">AUDITING_{id}</font>`），页面刷新后自动恢复
+ **优化**：轮询间隔从 30 秒优化到 5 秒（commit `<font style="background-color:rgba(0, 0, 0, 0.05);">59d1eb9</font>`），提升实时性

## 三、技术难点 & 算法类
### Q7: 签章画板的墨迹裁剪算法具体是怎么实现的？
**回答要点：**

+ **问题**：用户在手机上横屏手写签名，导出时需要自动裁剪空白区域并缩放到固定尺寸 378×157px
+ **算法步骤**（`<font style="background-color:rgba(0, 0, 0, 0.05);">cropAndResizeToFixedSize</font>` 函数）：
    1. **像素级扫描**：通过 `<font style="background-color:rgba(0, 0, 0, 0.05);">getImageData</font>` 遍历 Canvas 每个像素的 Alpha 通道，找到墨迹的 Bounding Box（minX, minY, maxX, maxY）
    2. **空白画布检测**：如果所有像素 Alpha 都为 0（完全没写字），直接返回原图，不做裁剪
    3. **等比缩放**：计算 `<font style="background-color:rgba(0, 0, 0, 0.05);">scale = min(availableW / cropW, availableH / cropH)</font>`，以不溢出任一维度为准
    4. **安全边距**：上下左右各留 10px padding，防止签名顶到边缘
    5. **居中绘制**：创建离屏 Canvas 378×157，计算偏移量 `<font style="background-color:rgba(0, 0, 0, 0.05);">dx = (targetW - drawW) / 2</font>`，将裁剪区域居中绘制
+ **横屏适配**：整个 UI 通过 CSS `<font style="background-color:rgba(0, 0, 0, 0.05);">transform: rotate(90deg)</font>` 旋转 90 度，提示文字也同步旋转，适配用户横握手机的书写姿势；导出前先调用 `<font style="background-color:rgba(0, 0, 0, 0.05);">getRotateCanvas(-90)</font>` 转回正向
+ **高清屏适配**：Canvas 初始化时 `<font style="background-color:rgba(0, 0, 0, 0.05);">scale: window.devicePixelRatio</font>`，保证 Retina 屏上无锯齿
+ **内存管理**：关闭弹窗时手动置空 `<font style="background-color:rgba(0, 0, 0, 0.05);">signature = null</font>`，移除 `<font style="background-color:rgba(0, 0, 0, 0.05);">touchstart</font>` 事件监听，并由父组件通过 `<font style="background-color:rgba(0, 0, 0, 0.05);">removeDOM</font>` 回调销毁 DOM 节点，防止内存泄漏

### Q8: 并发上传文件到腾讯云 COS 是怎么优化的？
**回答要点：**

+ **优化前**：多文件串行上传，一个接一个（`<font style="background-color:rgba(0, 0, 0, 0.05);">for + await</font>`），总耗时 = 单个耗时 × 文件数
+ **优化后**（commit `<font style="background-color:rgba(0, 0, 0, 0.05);">e007cf5</font>`）：
    - 先用 `<font style="background-color:rgba(0, 0, 0, 0.05);">handleFileUpload</font>`**并行**获取每个文件的 COS 临时凭证（独立接口，互不依赖）
    - 获取凭证后通过 `<font style="background-color:rgba(0, 0, 0, 0.05);">Promise.all(uploadTasks)</font>` 并发上传所有文件
    - 每个文件独立跟踪上传状态（`<font style="background-color:rgba(0, 0, 0, 0.05);">uploading</font>` / `<font style="background-color:rgba(0, 0, 0, 0.05);">success</font>` / `<font style="background-color:rgba(0, 0, 0, 0.05);">failed</font>`），单个失败不影响其他文件
+ **效果**：N 个文件上传时间从 O(N) 降为 O(1)，文件越多效果越明显

## 四、工程质量 & 稳定性类
### Q9: 灰度发布 / 功能开关是怎么实现的？
**回答要点：**

+ **优势**：支持按门店/用户维度灰度，出问题可秒级回滚（改字典值即可）

### Q10: 门店匹配逻辑中如何过滤无效门店？
**回答要点：**

+ **问题**：门店列表接口返回了已闭店、注销等无效门店，导致用户选择了无法使用的门店
+ **方案**（commit `<font style="background-color:rgba(0, 0, 0, 0.05);">a504792</font>`）：
    - 在默认门店匹配时增加过滤条件，排除闭店（`<font style="background-color:rgba(0, 0, 0, 0.05);">status</font>`）、注销等无效状态
    - 优先匹配最近使用的门店，其次匹配用户所属门店
+ **边界处理**：如果过滤后无可用门店，给出明确提示而非静默失败

### Q11: 如何防止关键操作（审方通过/驳回）的重复提交？
**回答要点：**

+ **操作锁模式**：`<font style="background-color:rgba(0, 0, 0, 0.05);">isActionLoading</font>` ref 作为互斥锁
    - 点击按钮时先检查 `<font style="background-color:rgba(0, 0, 0, 0.05);">isActionLoading.value</font>`，为 `<font style="background-color:rgba(0, 0, 0, 0.05);">true</font>` 则直接 return 不执行
    - 操作开始时设为 `<font style="background-color:rgba(0, 0, 0, 0.05);">true</font>`，完成或失败后设为 `<font style="background-color:rgba(0, 0, 0, 0.05);">false</font>`
    - 按钮 `<font style="background-color:rgba(0, 0, 0, 0.05);">:disabled="isActionLoading"</font>`，从 UI 层面双重保障
+ **人脸验证前置**：审方操作前必须先通过每日人脸验证，验证失败直接阻断，不再进入提交逻辑
+ **对话框 before-close 钩子**：`<font style="background-color:rgba(0, 0, 0, 0.05);">van-dialog</font>` 的 `<font style="background-color:rgba(0, 0, 0, 0.05);">before-close</font>` 回调中，如果 `<font style="background-color:rgba(0, 0, 0, 0.05);">isActionLoading</font>` 为 `<font style="background-color:rgba(0, 0, 0, 0.05);">true</font>`，阻止关闭对话框（`<font style="background-color:rgba(0, 0, 0, 0.05);">done(false)</font>`），防止误操作关闭导致状态不一致

### Q12: 这个项目没有自动化测试，如果要补测试，你会怎么设计测试策略？
**回答要点：**

+ **分层测试策略**：
    1. **单元测试**（Vitest）：工具函数（`<font style="background-color:rgba(0, 0, 0, 0.05);">pollUntilResolved</font>`、`<font style="background-color:rgba(0, 0, 0, 0.05);">cropAndResizeToFixedSize</font>`、`<font style="background-color:rgba(0, 0, 0, 0.05);">dict.ts</font>` 安全解析）、Vuex mutations/actions
    2. **组件测试**（Vue Test Utils + Vitest）：`<font style="background-color:rgba(0, 0, 0, 0.05);">DynamicForm</font>`（各种 field 类型渲染）、`<font style="background-color:rgba(0, 0, 0, 0.05);">SignatureBoard</font>`（mount/unmount 流程、事件模拟）
    3. **集成测试**：API 层（mock axios，验证拦截器逻辑、token 过期自动登出、错误 toast 行为）
    4. **E2E 测试**（Playwright）：关键业务流程——AI 处方全流程、审方通过/驳回流程、签章录入流程
+ **优先级**：先覆盖核心业务路径（审方、AI 处方），再补工具函数和边界 case
+ **挑战**：原生桥接层需要 mock（`<font style="background-color:rgba(0, 0, 0, 0.05);">window.android</font>`、`<font style="background-color:rgba(0, 0, 0, 0.05);">window.webkit</font>`），可以写一个测试专用 platform mock 注入到 `<font style="background-color:rgba(0, 0, 0, 0.05);">PlatformTool</font>` 中

## 七、开放性问题
### Q16: 你对医疗/处方业务的复杂度有什么理解？
+ **多角色协作**：医生开方 → 药师审方 → 店员提单 → 患者取药，每个角色有不同权限和操作
+ **合规要求**：人脸验证（药师每日验脸）、电子签章（监管要求）、处方图片存档
+ **渠道多样性**：O2O、B2C、粤医保、国家处方流转平台，各有不同的业务流程和 UI 规则
+ **时效性**：处方当日有效（`<font style="background-color:rgba(0, 0, 0, 0.05);">isExprie</font>` 判断），过期作废
+ **数据隐私**：患者姓名脱敏（只显示首字+星号）

### Q17: H5 内嵌在原生 App 中有哪些坑？
+ **iOS/Android 行为不一致**：JSBridge 调用方式不同（`<font style="background-color:rgba(0, 0, 0, 0.05);">window.android.xxx()</font>` vs `<font style="background-color:rgba(0, 0, 0, 0.05);">window.webkit.messageHandlers.xxx.postMessage()</font>`），返回值字段命名不一致
+ **WebView 兼容性**：不同版本的 WebView 对 CSS/JS 支持有差异，需要通过 `<font style="background-color:rgba(0, 0, 0, 0.05);">@vitejs/plugin-legacy</font>` 做降级
+ **原生导航冲突**：H5 路由跳转 vs 原生返回手势/NavBar，需要在 `<font style="background-color:rgba(0, 0, 0, 0.05);">App.vue</font>` 的返回逻辑中判断是否应该退出 App 还是回退路由
+ **键盘遮挡**：表单输入时原生键盘弹出遮挡输入框（Vant Form 组件自带处理）
+ **调试困难**：线上问题需要依赖 `<font style="background-color:rgba(0, 0, 0, 0.05);">vConsole</font>` 查看日志，无法使用 Chrome DevTools 真机调试
